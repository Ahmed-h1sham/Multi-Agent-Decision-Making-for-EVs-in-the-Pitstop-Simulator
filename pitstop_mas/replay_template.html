    Decisions over time

    Deciding later: the defer action

    An EV may wait where it is and decide again with newer information. Rule used here: if the EV would queue at least 5 min at its best station anyway, it waits at its own spot instead and decides again after that time, at most 3 times. It books nothing while it waits, its delay d keeps counting from the original request, and the time spent waiting uses up its patience.

    Learned decisions

    A learned policy: parameter-shared PPO

    Every EV uses the same small neural network to choose a station or defer, from the same observation the PettingZoo environment gives any controller. Its reward is minus its own access delay, the same objective the rules use. It is trained on scenarios that are never used for evaluation, then run without exploration on the evaluation scenarios above.

      Multi-agent interface

      The same simulator as a PettingZoo environment

      PettingZoo is the standard interface between multi-agent learning code and an environment. The simulation core is unchanged: the environment pauses it whenever an EV must decide, hands that EV its observation, applies its action and runs on to the next decision. A learned policy can therefore replace the decision rule while everything else stays identical.

      Agent definition

      AgentsOne per charging request. An EV joins when its need appears and leaves once it starts charging, gives up, or the run ends.
      Turn orderOne EV at a time, in the simulator's event order (PettingZoo AEC).
      ObservationPer station: reachable, travel time, projected start, queue length, idle chargers, EVs on their way (board settings only), charger power. Own: charge level, time since request, deferrals used, clock.
      ActionOne of the stations, or defer. A mask marks unreachable stations and, outside A_d / B_d, the defer action.
      RewardPaid when access is settled: minus the access delay d in hours; giving up adds a 2-hour penalty.
      SettingsA, B_info, B, A_d, B_d fix what EVs see and how stations serve; only the decision comes from the agent.

      Design decisions in the code

      Reservation contract and demo assumptions

      The background chapter says the contract must be fixed before evaluation. This is the version implemented in the demo; every value is a demo default that the methodology chapter can still change.

      Board service contract

      Resource bookedA place at a station. Vehicles choose stations, not chargers.
      VisibilityA booking is visible to every later decision immediately.
      ValidityFrom booking until the vehicle arrives.
      Arrival tolerance10 min after the expected arrival.
      Expiry / no-showAn unused booking lapses at its deadline; the driver becomes a walk-in.
      CancellationA driver who leaves the queue frees the place.
      ConflictsDecisions are processed one at a time in a fixed event order, ties by request id, so two bookings never race.
      Service ruleB: valid bookings in booking order, then walk-ins by arrival. B-info: plain FCFS. Both never hold a charger idle while a vehicle is present.

      Method values, fixed before the final run

      • Warm-up. Each run starts with empty stations. Requests in the first 4 h are simulated but not counted; Welch's procedure showed waiting settles within about 3.5 h at high demand.
      • Measured window. Requests made in the next 6 h are counted; the run continues 2 h longer so their sessions can finish.
      • Threshold τ = 15 min of queue waiting counts as excessive. Shares above 5, 10 and 30 min are also reported.
      • Patience. A driver leaves the queue after 15–60 min of waiting (uniform), the medium waiting tolerance in a 2024 survey of BEV drivers.
      • Demand levels. Normal ρ = 0.6, high ρ = 0.9, reduced capacity: normal demand with 3 of 10 chargers out of service for the whole run.
      • Seeds. The evaluation scenarios use a seed set never used while these values were chosen.
      • Still open. The hold rule; a centralised critic (MAPPO) for the learned policy.

      Agent interfaceNewPettingZoo multi-agent environment on the same core. The old environment was a single-agent Gymnasium environment.
      Learned policyNewParameter-shared PPO for many EVs with delayed rewards (NumPy). The old Q-learning and Stable-Baselines3 PPO code trains one vehicle and was not reused.

      Run it on your own machine

      Every number on this page comes from one command. The page itself is written by that command from the run's output.

      pip install -r requirements.txt  # numpy scipy pandas pytest pettingzoo gymnasium
python run_demo.py               # tests, Erlang C check, 30 paired scenarios per level, this page
python run_demo.py --m 10        # quicker run
python -m pytest -q tests        # validation tests only

# use the PettingZoo environment from your own code
from pitstop_mas.env import env
e = env(setting="B_d", level="high")
e.reset(seed=0)
for agent in e.agent_iter():
    obs, reward, done, cut, info = e.last()
    action = None if (done or cut) else my_policy(obs)   # obs["action_mask"] marks legal actions
    e.step(action)
